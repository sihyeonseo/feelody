# Feelody 평가 설계와 포트폴리오 증거

이 문서는 2026-11-04 검토한 토스 채용 자료 여러 발췌의 취지를 Feelody에 적용한 설계다. 특정 직무의 모든 요건을 충족했다는 의미가 아니다. [시스템 설계](system-design.md)는 구현 경계와 데이터 흐름을, 이 문서는 어떤 관찰로 모델과 운영 결정을 내릴지를 설명한다.

## 요구 역량을 무엇으로 보여줄까?

| 자료에서 읽은 역량 | Feelody에서 답할 질문 | 이력서에 붙일 증거와 현재 상태 |
|---|---|---|
| 문제 정의 → 가설 → 평가 → 실패·개선 | 상황이 달라도 감정이 맞으면 좋은 추천인가? 세 곡을 어떻게 평가할까? | 감정 중심 0~3점 기준, 실제 출력 채점, 반례. [10편 파일럿](../reports/top3_pilot.json)까지 있음 |
| 정성적 품질을 측정하고 불확실성을 설명 | AI가 고르지 않은 노래도 정답일 수 있는데 무엇을 세나? | 참고곡 일치와 사람 평가 분리. 독립 평가셋·복수 평가자 검증은 다음 단계 |
| 사용자에게 닿는 전체 시스템을 책임 | 모델 부재나 동시 요청에도 일기를 잃지 않는가? | 달력·저장·API·추천 코드 있음. 실제 배포 요청의 추적, 장애 검수, 사용자 피드백은 별도 증거 필요 |
| 품질·지연·비용의 선택 | 30곡 재순위화가 사용자의 대기시간만큼 가치가 있는가? | 검색만/재순위화 결과 있음. 같은 장치·같은 조건의 지연/비용표와 모델 채택 기록은 계획 |
| 최신 AI·LLM을 사용자 문제에 맞게 사용하고 운영 | 생성 모델을 추가해야만 해결되는 문제가 있는가? | 현재는 임베딩 검색과 판별형 재순위화다. AI 참고곡 생성은 데이터 준비이며 운영형 LLM·에이전트 경험이 아니다. 추후 도입한다면 별도 실험과 실제 운영 기록 필요 |

**선택 가능한 후속 연구:** 감정 판단의 근거를 남기기 어려운 경우, LLM이 오프라인에서 ‘일기–가사’의 감정 변화와 판정 근거를 초안으로 제안하고 사람이 수정하는 평가 보조 도구를 시험할 수 있다. 독립적인 사람 채점과 불일치율·검수시간·비용을 비교한다. 추천 후보를 만든 AI가 같은 후보의 최종 심판이 되지 않도록 분리한다. 설명 요구나 검수 이득이 관찰되지 않으면 도입하지 않는다.

| 검색이 못 찾았기 때문에 최종 세 곡이 실패했다 | 039번은 30곡 전수 채점에서 검색 19위·22위가 2점 이상, 최종 세 곡은 모두 0점 | 이 일기에는 재순위화 손실이 있다. 전체 실패 원인이나 장르 효과로 일반화하지 않는다 |

## 평가 계약: 세 곡 중 몇 곡을 실제로 권할 수 있는가?

- **주지표:** 일기별 `P@3 = (사람 감정 점수 ≥ 2인 추천 수) / 3`, 일기별 값을 평균한다. 전체 성공 요청의 최종 세 곡은 모두 채점한다. 생성/전송 실패율은 별도 분모(전체 요청)로 함께 보고한다.
- **채점:** 0=중심 감정이 어긋남, 1=일부분만 닿음, 2=중심 감정이 대체로 맞음, 3=감정의 강도·변화까지 설득력 있게 맞거나 변화 없는 정서를 잘 유지함. 상황·장르 차이 자체는 감점하지 않는다. 원문 가사를 기준으로 판단하고 애매한 이유를 적는다.
- **보조지표:** AI 참고곡 3개는 순위 없는 집합이다. MRR@3은 그중 처음 맞힌 검색 순위의 역수(없으면 0)이며, 미등록 참고곡·카탈로그 매핑률을 별도 보고한다. 후보 안에 사람이 확실히 적합하다고 본 곡이 있는데 놓쳤는지, 곡별 노출 쏠림, 세 곡 모두 부적합한 일기의 비율도 살핀다.
- **사용자 신호:** 실제 작성자의 곡별 ‘맞음’ 비율은 응답 수와 응답률을 붙여 별도 보고한다. 클릭이나 화면 체류시간은 감정 적합도의 정답이 아니다.

## 다음 실험: 검색 실패와 재순위화 실패를 분리한다

1. **대상/분리:** 기존 10편과 039번은 이미 여러 번 본 개발 사례다. 독립 평가용 현대 일기를 별도로 확보하고 유사·중복 일기와 동일 작성자(식별 가능한 경우)가 양쪽에 걸치지 않게 분리한다. 곡 ID 대신 같은 가사 그룹을 기준으로 참고곡 매핑과 중복 처리를 고정한다.
2. **동일 후보 대조:** 같은 일기의 원문, E5 revision, 인덱스, 후보 30개를 고정한다. A=검색 상위 3개, B=KURE 재순위 상위 3개. 모델명·점수·순위를 가린 합집합을 한 번만 채점한다. 실패 일기 일부는 후보 30개를 전부 채점하고, 실패만 선택했다면 전체 실패율 추정에 쓰지 않는다.
3. **진단:** 후보 내 2점 이상 수를 r이라 하면 현 후보에서 가능한 최고 P@3은 `min(r,3)/3`이다. r=0이면 현 후보에 적합 곡이 없음(카탈로그 전체에 없다는 뜻은 아님). 최고값과 실제값의 차이는 이미 검색된 곡을 정렬하며 잃은 몫이다. 미채점 후보가 남으면 이 최고값을 확정하지 않는다.
4. **개선안:** 후보에 적합 곡이 있으면 현재 512토큰 제한으로 결정적인 감정 대목이 잘렸는지 먼저 읽고, 같은 후보에서 ‘앞부분만’과 ‘앞·뒤 발췌’를 한 변수로 비교한다. 반대로 후보 안에 적합 곡이 없는 사례가 많으면 검색 모델 또는 쏠림 보정을 별도 실험한다. 가사 길이·장르별 실패는 사례와 분모를 함께 기록하고 랩 자체를 일괄 감점하지 않는다.
5. **검증:** 순서를 무작위화하고 일부는 두 평가자가 독립 채점해 점수 일치와 1↔2 경계 불일치를 기록한다. 같은 일기의 전후 P@3 차이, 개선/동률/악화 일기 수, 표본 수를 공개한다. 표본이 충분하면 일기 단위 paired bootstrap으로 구간을 산출한다. 탐색용 열 편의 작은 차이로 우월성을 선언하지 않는다.

### 배포 후보 선택 규칙 (제안)

| 항목 | 측정과 의사결정 |
|---|---|
| 품질 | 기존 30→3을 대조군으로 두고, 별도 일기에서 P@3과 전부 실패한 일기의 비율을 함께 본다. 개선이 불명확하면 현재 버전을 유지한다 |
| 시간 | 같은 장치에서 같은 짧은/긴 일기를 섞어 반복. 첫 요청(모델 로딩 포함)과 준비된 상태를 구분. 검색·재순위·전체의 p50/p95와 표본 수 기록. 현 UI의 120초 타임아웃은 품질 목표가 아니다. 사용자에게 허용되는 대기시간을 소규모 시연에서 확인해 다음 모델 비교 **전에** 한도를 고정 |
| 크기·비용 | 모델+인덱스 용량, 최대 RAM/VRAM, 일기 1편 처리 자원량 측정. 호스트 메모리 한도 초과 또는 자동 초과 청구가 가능한 공개 배포안은 무료 데모에서 제외. 숫자를 측정하기 전에는 ‘실시간’, ‘운영비 절감’ 등으로 표현하지 않는다 |
| 재현 | 데이터셋/채점 기준 버전·코드 SHA·모델 revision·인덱스 해시·후보 수·환경·예외/누락 수를 결과와 함께 저장. 비공개 원문 없이는 공개 집계 검산과 원실험 재실행이 다르다고 명시 |

## 지금 포트폴리오에 쓸 수 있는 문장

> 한국어 일기의 감정과 어울리는 K-pop 세 곡을 찾기 위해 원문 가사 2,242그룹을 대상으로 검색 30곡과 재순위화 3곡을 분리했다. 같은 일기 10편에서 사람이 2점 이상으로 평가한 추천은 검색만 적용했을 때 30자리 중 4개, 재순위화 후 10개였다. 한 실패 일기의 후보 30곡을 전수 검토해, 적합한 두 곡을 검색하고도 최종 추천에서 놓친 사례를 확인했다.

이후 실제 웹 요청이 추적되고 사용자 평가가 쌓이면 ‘얼마 동안, 몇 건, 어떤 환경에서, 무엇을 바꿔 결과가 어땠는지’를 덧붙인다. 현재는 [달력과 모델 API](system-design.md)를 **구현**, 요청 단위 추적과 피드백 운영을 **설계**, 공개 장기 운영과 일반화 성능은 **미검증**으로 표시한다.
